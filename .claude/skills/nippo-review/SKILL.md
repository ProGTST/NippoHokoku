# NippoHokoku コードレビュー

/code-review（正しさ・バグ検出のレビュー）と同じ進め方に、本プロジェクト固有の観点を加えてレビューする。
**レビューのみ行い、コードは修正しない**（修正はユーザーが指示した場合のみ）。

## 1. レビュー対象を決める

引数 `$ARGUMENTS` で対象を決める。

| 引数                      | 対象                                                                                                                       |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 省略                      | `git diff HEAD`（未コミット）＋ `git diff main...HEAD`（main 以降のコミット）。どちらも空なら直近1コミット `git show HEAD` |
| コミットハッシュ          | `git show <hash>`                                                                                                          |
| 範囲 `a..b`               | `git diff a..b`                                                                                                            |
| ファイル/ディレクトリパス | そのファイル全体（差分ではなく現状コード）                                                                                 |

- 差分だけで判断しない。変更箇所を含む関数全体と、その呼び出し元・呼び出し先を必ず読む（`Grep` で参照箇所を確認）。
- 冒頭で「対象: ○○（N ファイル / +X -Y 行）」を1行で示す。

## 2. 前提として読むもの

- 仕様書: `現行仕様.md`（既存システム rkanri の仕様・API）、`新仕様.md`（本アプリの仕様）、必要に応じて `置換調査.md`・`README.md`・`リリース手順.md`。変更箇所に関係する節だけ読めばよい。
- 規約: リポジトリ直下や親ディレクトリに `CLAUDE.md` があれば読む。無ければ「CLAUDE.md 規約」観点は下記の本プロジェクト規約で判断する。
- 構成: Electron（`main.js` / `preload.js`）＋ レンダラ（`src/index.html` / `src/renderer.js` / `src/styles.css`）。型は JSDoc ＋ `types/globals.d.ts` を `tsc --noEmit` で検査。

## 3. 観点（チェックリスト）

各観点の「本プロジェクトでの見方」に従う。**技術的に存在しない項目（例: Prisma の `$executeRaw`、BigInt を扱わない箇所）は無理に指摘しない**。該当なしの観点は報告表に載せない。

| 観点             | チェック内容                                                 | 本プロジェクトでの見方                                                                                                                                                                                                                                                                                                     |
| ---------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 型安全性         | createFetcher / as キャスト / BigInt                         | `/** @type {any} */` や `@returns {any}` での型逃げ、JSDoc キャスト `/** @type {X} */ (v)` の妥当性、`preload.js` と `types/globals.d.ts` の IPC 型の不一致、API 応答（`callApi` / `execApi`）を型確認せず使っていないか、`Number()` 変換で NaN を考慮しているか。fetch ラッパー（`apiGet`/`apiPost`）の応答チェック       |
| データ安全性     | 紛失・スコープ外の更新・一意制約                             | 一括変更/一括削除/一括コピーで選択外や他担当者の日報を更新・削除しないか（`selectedNippo`・`viewOnly`・担当者切替の状態）、入力中データがモーダル遷移・再読込で失われないか、日報コードの重複登録・二重送信（多重クリック）防止                                                                                            |
| CLAUDE.md規約    | Hex禁止 / 共通カラム / 共通コンポーネント                    | CSS で色を直書き（`#xxxxxx`）せず `:root` の CSS 変数を使っているか（既存の直書きは新規追加分のみ指摘）、既存の共通処理（`uiConfirm`・`toast`・`openModal`/`closeModal`・`renderTableInto`・`callApi`）を使わず独自実装していないか、native `confirm`/`alert` を使っていないか（webview フォーカス不具合の回避のため禁止） |
| 機能要件         | 設計書照合 / dltflg / $executeRaw戻り値 / mutate()           | 仕様書（現行仕様.md / 新仕様.md）の項目・キー名・API 送受信と一致しているか、API の業務エラー判定（`isBizOk` / `bizStatus`）を確認しているか、更新後に一覧を再取得（`loadList`）して画面を最新化しているか（= mutate 相当）                                                                                                |
| パフォーマンス   | N+1 / ループ内DB操作                                         | ループ内で API を逐次 await していないか（一括処理で件数分の通信が必要な場合は進捗表示・中断時の扱いがあるか）、行ごとに全件 `filter` する O(n²) 処理、描画のたびの不要な再計算・DOM 全再生成                                                                                                                              |
| コード品質       | DRY / デッドコード / console.log / デグレ防止 / バグや脆弱性 | 重複ロジック、未使用の関数・変数・CSS、デバッグ用 `console.log` の残置、既存機能（範囲選択・Ctrl選択・参照のみモード等）を壊していないか、`innerHTML` への未エスケープ値の挿入（XSS）、`executeJavaScript` への文字列連結注入、トークン等秘匿情報のコミット（`src/update-token.js`）                                       |
| 影響範囲         | 共通コンポーネント / CSS変数 / 型定義                        | `renderTableInto` など複数画面で使う関数の変更が他のテーブル（案件・担当者・一括変更）に波及しないか、汎用セレクタ（`th`, `td`, `tbody tr` 等）の CSS 変更の波及、`types/globals.d.ts` と preload/main の整合                                                                                                              |
| 仕様の一致       | 仕様と乖離がないか / コメントの古い記述                      | 実装と仕様書の差異、変更で古くなったコメント・JSDoc・仕様書の記述が残っていないか（例: 列を削除したのにコメントに旧列名が残る）                                                                                                                                                                                            |
| エラーの握り潰し | わからない状態にしていないか                                 | 空の `catch {}`、`catch` で `return` だけして利用者にもログにも出さない処理、`.catch(() => {})`、失敗時に成功扱いで進む分岐、`callApi(..., silent=true)` で失敗が見えなくなる箇所                                                                                                                                          |

## 4. 進め方（/code-review と同じ）

1. **候補の洗い出し**: 対象コードを上表の観点ごとに読み、問題候補を挙げる。
2. **裏取り**: 各候補について実際のコード（呼び出し元・データの流れ・既存の防御処理）を読み、本当に問題になるか確かめる。具体的な入力・操作手順で「何が起きるか」を説明できない候補は捨てる。推測の指摘は出さない。
3. **重要度付け**:
   - **高**: データ紛失・誤更新・他人のデータ変更、クラッシュ、セキュリティ、仕様と明確に異なる動作
   - **中**: 特定条件で起きる不具合、エラーの握り潰し、影響範囲の波及、型安全性の穴、性能劣化
   - **低**: 可読性・DRY・古いコメント・規約違反（動作影響なし）
4. 必要なら `npm run typecheck` と `npm run format:check` を実行し、結果も判断材料にする（エラーが出たら指摘に含める）。

## 5. 出力形式

重要度の高い順に、次の表で報告する。チケットNo は `#1` からの連番。

| #   | 重要度 | 問題事項                                       | 根本原因         | 対策/修正案                    | 修正箇所              | 観点         |
| --- | ------ | ---------------------------------------------- | ---------------- | ------------------------------ | --------------------- | ------------ |
| #1  | 高     | （何が起きるか。再現手順・入力を含め具体的に） | （なぜ起きるか） | （どう直すか。短いコード例可） | `src/renderer.js:123` | データ安全性 |

- **修正箇所** は `ファイルパス:行番号` 形式（クリックで開けるよう Markdown リンク `[renderer.js:123](src/renderer.js:123)` にする）。複数ある場合は改行（`<br>`）で列挙。
- **観点** は第3章の観点名から1つ（複数該当なら主なもの）。
- 表の後に、指摘件数のまとめ（高 n / 中 n / 低 n）と、確認したが問題なしとした主な観点を1〜2行で書く。
- 指摘が0件なら表は出さず「指摘事項なし」と、確認した観点を書く。
- 修正はしない。最後に「どのチケットを修正するか」をユーザーに確認する。
